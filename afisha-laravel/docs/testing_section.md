2.7 Автоматизированное тестирование системы

2.7.1 Общие сведения

Помимо ручного функционального тестирования методом «чёрного ящика», для системы
«АфишаКолыма» разработан набор автоматизированных тестов. Автоматизация позволяет
многократно и без участия человека проверять корректность ключевых сценариев работы
серверной части после внесения изменений в код, что снижает риск регрессионных
ошибок.

Тесты написаны на фреймворке PHPUnit, интегрированном в Laravel. Каждый тест
обращается к REST API приложения так же, как это делает браузер: формирует
HTTP-запрос (методы postJson, getJson, putJson), а затем сравнивает фактический
HTTP-код ответа и содержимое базы данных с ожидаемыми значениями.

Тесты выполняются в изолированной среде: вместо боевой СУБД MySQL используется
встроенная база данных SQLite, размещаемая целиком в оперативной памяти (in-memory).
Перед каждым тестом схема базы данных создаётся заново и заполняется справочными
данными (роли, статусы, категории), а после теста уничтожается. Благодаря этому
тесты не зависят друг от друга и не затрагивают реальные данные. Отправка
электронной почты в тестовой среде перехватывается (Mail::fake) и проверяется без
фактической доставки писем.

Запуск всего набора тестов выполняется одной командой:

Листинг 2.7 — Команда запуска автоматических тестов

php artisan test

Базовый класс TestCase подготавливает окружение для каждого теста: создаёт схему
базы данных переносимыми средствами построителя Schema, заполняет справочники и
предоставляет вспомогательные методы createUser(), createOrg() и createEvent() для
быстрого создания тестовых сущностей.

Пример теста, проверяющего регистрацию пользователя с корректными данными,
приведён в листинге 2.8.

Листинг 2.8 — Тест регистрации пользователя (AuthTest.php)

public function test_register_with_valid_data_returns_token(): void
{
    $response = $this->postJson('/api/auth/register', [
        'first_name' => 'Иван',
        'phone'      => '+79001234567',
        'password'   => '123456',
        'pd_consent' => true,
    ]);

    $response->assertStatus(201)
        ->assertJsonStructure(['data' => ['token', 'user']]);
    $this->assertDatabaseHas('users', ['phone' => '+79001234567']);
}

2.7.7 Дефект, выявленный автоматическими тестами

В процессе прогона автоматических тестов был обнаружен дефект в модуле
восстановления пароля. Проверка срока действия ссылки сброса была реализована
следующим образом:

Листинг 2.9 — Исходный (ошибочный) код проверки срока действия токена

if (now()->diffInMinutes($record->created_at) > 60) {
    // ссылка считается просроченной
}

В используемой версии библиотеки дат Carbon 3 метод diffInMinutes() возвращает
знаковую разницу: для момента времени в прошлом результат получается
отрицательным. В результате условие «> 60» не выполнялось никогда, и просроченные
ссылки для сброса пароля принимались системой как действительные, что является
уязвимостью безопасности.

Тест TC-09 («сброс пароля по истёкшему токену») зафиксировал расхождение
ожидаемого и фактического результата. Дефект устранён добавлением параметра
абсолютной разницы:

Листинг 2.10 — Исправленный код проверки срока действия токена

if (now()->diffInMinutes($record->created_at, true) > 60) {
    // ссылка считается просроченной
}

После исправления тест TC-09 успешно пройден. Данный случай подтверждает
практическую пользу автоматизированного тестирования: ошибка в логике
безопасности была выявлена до развёртывания системы.
